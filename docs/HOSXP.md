# อ่านวันนัดจาก HOSxP

`GET /api/v1/hosxp/oapp?from=2026-10-01&to=2026-10-31` อ่านข้อมูลนัดจาก `oapp` โดยตรง ต้องล็อกอินและมีสิทธิ์ `appointment.read` กับ `employee.read` ตามระบบเดิม

ตั้ง `HOSXP_DB_*` ใน `.env` ของ server โดยใช้บัญชีที่มีสิทธิ์ SELECT บน `oapp` และ `patient` ของ HOSxP แล้ว restart app ฐานนี้แยกจาก `DB_*` ของเว็บ ไม่ต้อง migrate ฐาน HOSxP

การจับคู่ใช้ `oapp.hn = patient.hn` และ `patient.cid` ตรงกับ CID ที่ตรวจรับแล้วในทะเบียนบุคลากรเดิม จำกัดบุคลากรที่เปิดใช้งานและหน่วยงานตามสิทธิ์ ไม่สร้างทะเบียนผู้ป่วยเพิ่ม ไม่คืน CID/HN หรือหมายเหตุทางคลินิกไปยัง browser ไม่มีการเขียนกลับ HOSxP

ใช้ `nextdate` เป็นวันนัด และ `nexttime` เป็นเวลานัด (คง null เมื่อ HOSxP ไม่ระบุ) ไม่ใช้ `vstdate` แทนวันนัด ส่ง `oapp_id` เป็น string เพื่อรักษาเลขเต็ม เก็บรหัสคลินิกและแผนกตามต้นทาง ส่วนสถานที่ใช้ `contact_point`

ไม่ระบุช่วงวันที่จะอ่านตั้งแต่วันนี้ตามเวลาไทยถึงอีก 30 วัน จำกัดช่วงสูงสุด 366 วันและผลลัพธ์ 1,000 นัด หากเกินจะแจ้งให้ลดช่วงวันที่แทนการตัดข้อมูลเงียบ ๆ

`source_status_id` คืนค่าจาก `oapp_status_id` ตามจริง ไม่เดาว่ารหัสใดคือยกเลิก CSV ตัวอย่างมีสถานะเป็น NULL และไม่มีตาราง patient จึงต้องตรวจชื่อคอลัมน์ `patient.hn`, `patient.cid` กับฐานจริงก่อนใช้งาน

## เปลี่ยนจากการนัดในเว็บ

เมนู **นัดหมายจาก HOSxP** อ่านข้อมูลต้นทางโดยตรง ไม่มีปุ่มสร้าง เลื่อน หรือยกเลิกนัด และเอาเมนูนำเข้านัด Excel ออกแล้ว API สร้าง/แก้ไข/เปลี่ยนสถานะนัดและนำเข้า Excel เดิมตอบ 410 แม้เรียกตรง ผู้ใช้จัดการนัดทั้งหมดใน HOSxP ส่วนทะเบียนบุคลากร CID และ provider หมอพร้อมใช้ของเดิม

ข้อมูลนัดและรายงานเดิมยังอยู่เพื่ออ่านย้อนหลัง ไม่มีการลบประวัติ ปฏิทินหน้าแรกแสดงภาพรวมนัดจาก HOSxP ที่ worker อ่านล่าสุด โดยไม่มีชื่อหรือ CID ส่วนรายงานข้อมูลเดิมยังแสดงประวัติในฐานเว็บเดิม

## เปิดใช้งานบน server

1. หยุด app/worker รุ่นเดิม สำรองฐานเว็บ แล้วอัปเดตโค้ด
2. ตั้ง `HOSXP_DB_*` แยกจาก `DB_*` และตรวจ `HOSXP_ACTIVE_STATUS_IDS` ให้ตรงกับรหัสที่หมายถึงนัดใช้งานจริงของโรงพยาบาล ค่าเริ่มต้น `NULL` อ้างอิง CSV ที่ให้มา รหัสอื่นจะไม่ส่งแจ้งเตือนจนกว่าจะตั้งค่า ไม่ใส่ credential ใน Git
3. รัน `npm run db:migrate` ในฐานเว็บ เพื่อสร้าง snapshot และเชื่อมคิวแจ้งเตือนกับ `oapp_id` โดยไม่เขียนฐาน HOSxP
4. รัน `npm run build` แล้วเริ่ม app และ `npm run worker:once` เพื่อบันทึกข้อมูลตั้งต้น การอ่านครั้งแรก **ไม่ส่งนัดที่มีอยู่ย้อนหลังทั้งหมด** ตรวจจำนวนและรายชื่อจากหน้าเว็บก่อนเปิด worker ต่อเนื่อง
5. ใช้การตั้งค่า LIVE/DRY_RUN, CID ที่ตรวจรับ และการเปิดรับข้อความในทะเบียนเดิม รัน `npm run worker` แล้วลงนัดทดสอบสำหรับบุคลากรทดสอบใน HOSxP

worker อ่านนัดตั้งแต่วันนี้ถึงอีก 366 วัน พัก 15 วินาทีระหว่างรอบ เมื่อพบเลขนัดใหม่ หรือวัน/เวลา/สถานที่/สถานะนัดเปลี่ยน จะสร้างคิวทันทีและใช้ตัวส่งหมอพร้อมเดิม ไม่รอเวลาส่งเตือนล่วงหน้าแบบเดิม ระยะเวลาถึงการส่งจริงขึ้นกับเวลาที่ใช้ query และจำนวนข้อความในคิว ไม่ใช่ database trigger

ใช้ `oapp_id` + รุ่นของข้อมูลนัดกันส่งซ้ำเมื่ออ่านข้อมูลเดิม การแก้หมายเหตุหรือ `update_datetime` อย่างเดียวไม่ส่งซ้ำ ก่อนส่ง LIVE ตรวจนัดกับ HOSxP อีกครั้ง หากนัดถูกลบ/เลื่อน/CID ไม่ตรงจะยกเลิกคิวเดิม หากฐานต้นทางติดต่อไม่ได้จะหยุดรอบและคงคิวไว้ ไม่ส่งข้อมูลที่ยืนยันไม่ได้ สถานะ UNKNOWN ของหมอพร้อมไม่ retry อัตโนมัติ

เมื่อปิดแจ้งเตือน ระบบยังอัปเดตตารางนัด แต่ไม่สร้างคิวสำหรับการเปลี่ยนแปลงระหว่างปิด เมื่อเปิดใหม่ไม่ส่งย้อนหลังช่วงที่ปิด ใน DRY_RUN ไม่มี HTTP ไปหมอพร้อม เช่นเดียวกับระบบเดิม

การ GET จากหน้าเว็บไม่ส่งข้อความ การส่งเกิดเฉพาะ worker ที่ผ่านการตั้งค่าเปิดใช้เดิมเท่านั้น

## การตรวจสอบ

ทดสอบเฉพาะข้อมูลสมมติด้วย `npm test` และ `npm run test:integration` ตาม test database guard เดิม การทดสอบ integration ใน `tests/integration/hosxp.test.ts` ครอบคลุม baseline, อ่านซ้ำ, worker สองตัว, เลื่อนนัด, ลบนัด และฐานต้นทางล่ม ต้อง migrate ฐานทดสอบก่อนรัน ห้ามใช้ฐานจริง
